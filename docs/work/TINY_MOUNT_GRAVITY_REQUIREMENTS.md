# Tiny Mount arbitrary-gravity requirements

Status: **TEMPORARY execution requirements — DELETE ON SUCCESS**.

Purpose: make Scale Brews' own mount mechanics respect arbitrary cardinal gravity while preserving the external contract that a Tiny Mount is simply a mount. This work must remain independently mergeable to Scale `main` and later be reconciled with the in-progress `chatgpt-editing` gravity-frame architecture.

## 1. Functional requirements

- **TGR-001 Generic mount contract.** A Tiny Mount must remain an ordinary vanilla passenger/vehicle relationship at the integration boundary. External consumers such as Clinging must not need a Tiny-Mount-specific gravity API, capability marker, version probe or alternate mount channel.
- **TGR-002 Native mechanic ownership.** Scale Brews owns the correctness of movement/impulses generated by Scale-specific Tiny Mount mechanics under arbitrary cardinal gravity. Clinging must not be required to patch bee flight, chicken glide, wolf pounce/landing or equivalent Scale-generated contributions.
- **TGR-003 Subsystem boundary.** Gravity-aware Tiny Mount mechanics belong to Scale's mount/integration layer, not the entity-collision solver. Tiny Mounts and anatomical support remain distinct systems.
- **TGR-004 Effective root frame.** Tiny Mount control/forces must be interpreted using the effective gravity frame of the root mount when an external gravity provider is available.
- **TGR-005 DOWN equivalence.** With DOWN/vanilla gravity, behavior must remain observably equivalent to current Scale behavior.
- **TGR-006 New impulses only.** Changing gravity does not rotate existing world-space momentum retroactively. Only newly generated mount control vectors/impulses are transformed from local gravity coordinates into world coordinates.
- **TGR-007 Bee/look-directed flight.** New flight velocity generated by Tiny Mounts must express rider-intended yaw/pitch in the root mount's gravity frame while preserving existing speed/max-pitch/max-vertical-speed policy.
- **TGR-008 Chicken glide.** Chicken glide damping and its jump-held/released behavior must act along local gravity vertical, not hardcoded world Y, for all six cardinal frames.
- **TGR-009 Wolf pounce.** Wolf pounce launch and landing cleanup must act in the root wolf's gravity frame while preserving attack/cooldown/damage semantics.
- **TGR-010 Mixed rider/root frames.** Mount mechanics use the root mount's physical frame, not the rider's frame merely because the rider supplies controls.
- **TGR-011 Frame changes mid-action.** A frame change between control samples affects subsequent generated impulses deterministically and must not double-transform or reinterpret already applied movement.
- **TGR-012 Optional gravity provider.** Scale must remain fully loadable and functional without Gravity Changer. Absence of an external provider yields the vanilla/DOWN frame.
- **TGR-013 Gravity Changer integration.** When Gravity Changer is present, Scale may install/use an optional reusable adapter that reads effective entity gravity without requiring Clinging. Gravity Changer must not become a required dependency.
- **TGR-014 Single authority.** Scale has one canonical gravity-frame reader/provider service. `collision` and `mount` may consume it, but they must not maintain separate registries/readers that can disagree.
- **TGR-015 Provider ownership.** Installing a second different provider owner fails explicitly; repeating installation by the same owner is idempotent, preserving the intent of entity-collision FR-073.
- **TGR-016 No Tiny-specific consumer contract.** Scale must not expose a Tiny-Mount-specific compatibility capability solely so Clinging can branch around Scale versions. Correctness is achieved by Scale honoring the mount root's gravity while Clinging continues to treat the root as an ordinary mount.
- **TGR-017 Regression-reference use only.** Clinging's current `ScaleFlightGravityMixin`, `ScaleWolfGravityMixin` and `ScaleChickenGravityMixin` may be used as historical regression evidence for intended outcomes, but not as implementation specifications or permanent compatibility surfaces.
- **TGR-018 No collision dependency.** Native Tiny Mount gravity support must not require the new entity-collision subsystem to be READY/active. It may share a transversal gravity-frame service but not contact/carry/anatomy lifecycle.
- **TGR-019 Future `chatgpt-editing` reconciliation.** When `main` changes are incorporated into `chatgpt-editing`, the collision branch must adopt/delegate to the same canonical gravity-frame service rather than retain `collision.internal.GravityFrames` as a competing authority.
- **TGR-020 Generic mounted integration proof.** A Tiny Mount under non-DOWN gravity must remain a normal vehicle/root from an external consumer's perspective. A bounded cross-repo fixture may verify this, but production Scale must not depend on Clinging.
- **TGR-021 Documentation truth.** After successful implementation/merge, permanent Scale docs must describe gravity-aware Tiny Mount mechanics and optional Gravity Changer integration without claiming entity-collision G7 completion or a special Clinging↔Tiny Mount protocol.

## 2. Non-functional requirements

- **TNFR-001 No hard dependency.** Base build/runtime without Gravity Changer remains valid.
- **TNFR-002 Deterministic transforms.** Six-frame transformations use one tested conversion path; no per-mob duplicated coordinate formulas where a shared helper is sufficient.
- **TNFR-003 Bounded compatibility logic.** Optional-mod detection occurs at initialization/cached boundaries, not repeated reflective discovery in hot movement loops.
- **TNFR-004 No double transformation.** Scale transforms only contributions that Scale itself generates. External gravity ownership changes the frame but does not cause a second transform of existing world momentum or of movement already expressed in world coordinates.
- **TNFR-005 Reviewable migration.** Changes are split by service boundary, mechanic migration and docs. No force-push/history rewrite.
- **TNFR-006 Main-safe independence.** The work must be implementable/validatable from Scale `main` without depending on unstable `chatgpt-editing` internals.
- **TNFR-007 Contract simplicity.** The external mounted contract remains ordinary Minecraft vehicle/passenger semantics plus effective entity gravity; no Tiny-specific integration contract is introduced unless a proven technical blocker makes that unavoidable and is documented first.

## 3. Acceptance outline

Adversarial regression coverage must include all six frames, DOWN equivalence, rider/root frame disagreement, frame change between actions, no provider present, provider present, ordinary unmounted behavior, and protection against double-transforming existing momentum. A bounded integration fixture should demonstrate that an actual Tiny Mount can be treated as an ordinary mounted `LivingEntity` root without any Tiny-Mount-specific branch in the consumer.
