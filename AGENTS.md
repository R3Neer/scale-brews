# Working on Scale Brews

- Read `TODO.md` and `CONTRIBUTING.md` before changes. `TODO.md` is an active-work index, not a requirements archive.
- For entity collisions, read `docs/ENTITY_COLLISIONS_REQUIREMENTS.md`, `docs/ENTITY_COLLISIONS.md`, `docs/ENTITY_COLLISIONS_PLAN.md`, `docs/ENTITY_COLLISIONS_FOUNDATION_AUDIT.md`, `docs/ENTITY_COLLISIONS_SPRINT_WORKFLOW.md` and `docs/VALIDATION.md` in that order. Do not recreate parallel anatomy/platform plans or status diaries.
- **`main` is an independently evolving product line, not a frozen baseline owned by the entity-collision branch.** Before planning, rebasing, merging, cleanup or destructive refactors in `chatgpt-editing`, inspect the current `main` and preserve gameplay/config/input/render/mount/gravity/inventory/reach changes that are outside the collision subsystem. Unfamiliar code that arrived on `main` must not be deleted, reverted or "restored" merely because an older collision document does not mention it. Integrate around current mainline behavior unless a canonical entity-collision requirement explicitly conflicts with it. This rule is rolling: more unrelated `main` changes are expected while the collision project remains in progress.
- **Every entity-collision task must identify the active role before modifying code: `IMPLEMENTER` or `ADVERSARY`.** The two roles may work on the same sprint/branch, but their responsibilities are different and must stay visibly separated in sprint docs, commits and evidence.
  - **IMPLEMENTER:** owns production changes required by the converged sprint plan. It may add implementation-facing tests and diagnostics needed to develop safely, but it must not design against unrevealed adversarial holdouts or rewrite adversarial evidence merely to make production pass.
  - **ADVERSARY:** owns independent review, holdouts, adversarial tests, fixtures, mutation/fault checks, reproducible probes, visual/snapshot verification and test infrastructure. Unless the task explicitly changes its role, it **must not fix production code** after finding a defect; it should make the defect observable, classify it and return it to the implementation phase.
  - The adversary is explicitly allowed to create test-only or temporary tooling when ordinary tests are too weak: harnesses, debug visualizers, capture programs, replay drivers, fuzzers, fixture generators, protocol inspectors, comparison tools and temporary CI workflows. Temporary infrastructure must be removed after capturing durable evidence unless it is genuinely reusable; reusable tools may remain under an appropriate test/tooling surface.
  - The adversary should use deterministic **visual snapshots** whenever the property is spatial, temporal, animated, compositional or otherwise capable of looking wrong while numeric assertions still pass. Snapshots may be Minecraft screenshots, collision/debug overlays, rendered geometry comparisons, contact sheets or frame sequences. Fix camera/view, tick/time, seed/state and inputs; compare against a reference/baseline; store enough metadata to reproduce the capture. Visual evidence supplements, rather than silently replaces, required machine-verifiable assertions.
- **Before any new entity-collision implementation sprint, execute and close S00 exactly as required by `docs/ENTITY_COLLISIONS_FOUNDATION_AUDIT.md`.** Existing collision code, primitives and historical green tests are candidates for reuse, not trusted foundations. Build the first adversarial model clean-room from current requirements and architecture before using historical tests as a source of cases; classify foundational components as `TRUSTED`, `REWORK`, `REPLACE` or `UNPROVEN`; repair blocking foundations before S01; and do not begin G1+ feature work while any foundation required by the next sprint remains `UNPROVEN`.
- Entity-collision implementation after S00 must follow `docs/ENTITY_COLLISIONS_SPRINT_WORKFLOW.md`: select a small dependency-coherent sprint, converge the implementation plan and pre-implementation adversarial model iteratively, implement iteratively, build adversarial tests afterwards, classify every failure before returning to the appropriate phase, and close only after a complete review pass produces zero changes. Sprint documents are execution records, not competing sources of requirements, architecture, roadmap or evidence.
- New requirements supplement unfinished work unless explicitly cancelled, but they belong in the canonical requirement source for their subsystem before plan/code changes.
- The owner may authorize autonomous implementation and scoped pushes. **The branch named by the current task is authoritative and overrides standing/default push guidance.** Do not force-push, rewrite history, create releases or tags without a separate request.
- Verify version-sensitive Minecraft/Fabric APIs against this project's 26.2 sources and dependencies.
- Keep registries, brewing, scale state and physical mechanics separate. Mixins should delegate rules to helpers rather than owning alternate implementations.
- Keep existing attribute balance unless rebalancing is explicitly in scope. Special head scaling is cancelled.
- Run the build/server GameTests and the client GameTest when changing shared/client mixins or resources. Record only executed results in `docs/VALIDATION.md`.
- The checkout deliberately lives in OneDrive. Use the optional `scalebrewsBuildDir` property for local generated output if necessary; do not move the source repository or delete broad cache directories.
- Art is original geometric pixel art from `tools/GenerateArt.java`, not image-generation models. Keep its generator and PNGs synchronized.
